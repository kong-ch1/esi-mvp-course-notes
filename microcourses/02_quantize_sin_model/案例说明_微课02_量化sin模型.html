1这个方案到底在做什么

一句话：把微课 01 训练出来的 32 位浮点模型，压缩成 8 位整数的格式，让 ESP32-S3 芯片跑得动。

为什么非要压缩？

ESP32-S3 是一颗微控制器，不是电脑。它的内存以"几百 KB"计，算力只有电脑的零头，而且很多型号根本没有浮点运算单元——让它算小数乘法，得用软件模拟，慢几十倍。

但神经网络训练出来全是浮点数（如 0.0374）。怎么办？量化：把这些浮点数"翻译"成整数。

量化到底在做什么（一个比喻）

想象把一把"毫米刻度的尺子"换成"厘米刻度的尺子"。测量范围还是那么长，但刻度变粗了，读数必然有误差。

量化的本质就是：先量出这批数据的最大最小值（定标），然后把浮点区间均匀切成 256 份（8 位能表示 0~255），每一份对应一个整数。之后模型里所有运算都用整数做，最后再按比例还原回浮点。

代价 = 精度损失；收益 = 体积变小、速度变快、能耗降低。

本课用的量化方式：PTQ（训练后量化）

方式怎么做特点
PTQ（本课用）模型已训好，喂一批数据统计范围，直接转整数快、不用重训、精度略降
QAT训练时就把量化误差算进去精度更好，但要重训，课程不涉及

本课要"喂进去统计范围"的那批数据，就叫校准数据（calibration data）。这里没有真实数据集，就现算 1000 个 sin 采样点当校准集——这也是后面所有麻烦的源头。

为什么量化不用 GPU？

训练要 GPU，是因为要反向传播——对几万个参数求梯度，迭代几百上千次，矩阵运算量巨大。

而量化只做前向传播：把 1000 个样本喂进去，记录每一层输出的最大值最小值，算完就结束。没有梯度、没有迭代、只跑一遍。所以 CPU 足够，脚本里也直接写死了 device="cpu"。

坑 2 ｜ README 第 3 步会降级 setuptools

和微课 01 是同一个坑：环境里 setuptools 是 83.0.0，torch==2.11.0 要求 <82。装依赖的唯一效果就是把它降级，其余 6 个包全是 already satisfied。降级 = 先卸后装，容易把包删成"半残"。

坑 3 ｜ README 的代码解析漏了一个 [0]

现象

README 的"关键代码解析"里贴的是 y_pred = executor(batch_x)，但脚本第 96 行实际写的是 criterion(y_pred[0], batch_y)。

PPQ 的 executor() 返回的是一个列表，不是张量。照 README 抄会直接报错。文档和代码不一致时，以代码为准。

坑 4 ★ ｜ 老师脚本的 collate_fn 写错了，而且是静默的

问题代码（脚本第 14 行附近） 
def collate_fn(batch):
    return torch.stack([sample[0] for sample in batch])

这个函数的写法，假设了 batch 是一串"样本"（每个样本是 (x, y) 这样的元组），所以它取每个样本的第 0 项再堆起来——这是标准 DataLoader 的 collate_fn 写法。

但 ESP-PPQ 传进来的根本不是样本列表。看 PPQ 源码（quantization/optim/calibration.py）：

for data in dataloader:          # data 已经是 DataLoader 拼好的 batch
    if self._collate_fn is not None:
        data = self._collate_fn(data)   # 再调用一次
    executor.forward(inputs=data, ...)

也就是说，PPQ 的 collate_fn 拿到的是"已经拼好的整批数据"，它的职责只是做预处理（转数据类型、搬到设备上），不是拼 batch。名字有误导性——它不是 DataLoader 的那个 collate。

PPQ 官方示例里写得很清楚：

def collate_fn(batch: torch.Tensor) -> torch.Tensor:
    return batch.to(DEVICE)

那为什么本课没崩？

因为恰好形状凑巧。本课的 DataLoader 每个 batch 返回 [(32,1), (32,1)]——x 和 y 都是形状 [32,1]。老师的 collate_fn 取 batch[0] 和 batch[1]，再 torch.stack 起来，得到 (2,1)。

这意味着什么（重要） 
DataLoader 给出的 batch : [(32,1), (32,1)]
老师 collate_fn 的输出 : (2, 1)      ← 模型实际拿到的是这个
正确应该是             : (32, 1)

两个张量形状都是 [1]，stack 得通，所以不报错。但含义完全变了：模型实际被喂进去的是 [x[0], y[0]]——把一个标签值当成了输入。

后果：校准数据的取值范围被污染了（x 原本在 [0, 2π]，现在混进了 y 的 [-1.05, 1.05]）。

但结论依然成立：老师提交的产物也是用同一份代码跑出来的，所以"我的 exponents 与老师完全一致"这个对拍结论没问题。需要修正的只是措辞——不能说"校准数据正确"，只能说"与老师一致"。

坑 5 ｜ 三个产物 MD5 全不同，是不是跑错了？

现象
文件我的老师的差
sin_model.espdl7696768016 B
sin_model.json90328757275 B
sin_model.info2664726259388 B

三个产物字节数全不同，第一反应是"我跑错了"。逐层拆解后，结论完全相反：

#差异来源解释
1行尾符老师的产物是 LF（Linux 风格），本机生成的是 CRLF（Windows 风格）。.info 的 388 字节差 = 388 行 × 1 字节，100% 是行尾符（26259 + 388 = 26647，分毫不差）
2hash 字段.json 里 68 行差异全是 "hash" / "dominator" 字段，没有一个是 exponent 或 scale
3列出顺序.info 里变量的打印顺序不同（老师是 fc2.weight→fc3.weight→fc3.bias；我的是 fc2.weight→fc2.bias→…）

那个 hash 是什么？

查 PPQ 源码 esp_ppq/core/quant.py 第 707 行：

_hash_seed = int(time.time())

用的是当前时间戳当随机种子。每次运行都不一样，和数值毫无关系。所以这个字段的差异不是"跑错了"，是"本来就不可能一样"。

那真正重要的东西一样吗？

一样。而且是逐位一致

把两边 .info 里所有 exponents: [...] 排序后对比 → 完全一致。

所有 value: array([...])（量化后的 INT8 / INT32 权重）排序后对比 → 完全一致。

由此得到一个反直觉但很扎实的结论

量化比训练更可复现。

微课 01 里，浮点训练跨机器会差 1e-6，导致数值产物逐字节不同。同样的浮点扰动进到量化这一步，因为量化是"定标 + 取整"的粗粒度操作，1e-6 被直接吸收掉了——量化参数和 INT8 权重跨机器完全一致，剩下的差异全是"非数值"的（行尾符 / 时间种子 hash / 打印顺序）。

5这一课收获了什么

  1. 理解了量化的本质：定标（量范围）+ 取整（切 256 份）。用"毫米尺换厘米尺"就能记住。
  2. 知道了代价与收益的量化表达：精度 1.44× 代价，换来体积压到 42.2%。
  3. 学会了用"拆解"代替"猜"：产物对不上时，不猜"是不是跑错了"，而是逐字段拆——行尾符、hash、顺序，一个个排除。
  4. 知道了 collate_fn 在不同框架里含义不同：DataLoader 的 collate 是"拼 batch"，PPQ 的 collate 是"预处理已拼好的 batch"。遇到"函数被框架反复调用"的报错，先读框架源码确认契约，不要假设参数含义。
  5. 知道了文档要"以代码为准"：README 的代码解析漏了 [0]，照抄会报错。
