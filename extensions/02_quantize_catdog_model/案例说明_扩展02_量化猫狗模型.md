## 1 这个方案到底在做什么

一句话：**把扩展 01 训练出来的猫狗模型（8.8 MB 浮点），压缩成 8 位整数格式，让 ESP32-S3 装得下、跑得动。**

它和微课 02 是同一件事（PTQ 训练后量化），但**难度完全不是一个量级**：

|  | 微课 02（sin） | 扩展 02（猫狗） |
| --- | --- | --- |
| 模型 | 3 层全连接 | **MobileNetV2，53 层卷积** |
| 输入 | 1 个数字 | **1×3×224×224 的图片** |
| 校准数据 | 现算 1000 个点 | **真实图片，要先读进来、裁剪、归一化** |
| 输入体积 | 18244 字节 | **8,878,502 字节**（差 487 倍） |
| 耗时 | 几秒 | **几分钟到几十分钟** |

所以这一课真正的新东西不是"量化"本身，而是**图像预处理管线**——数据要从磁盘读进来、缩放成 224×224、转成张量、按 ImageNet 的均值方差归一化，才能喂给模型。链路一长，出错的地方就多了。

> **【说明】**
>
> **量化复习：定标 + 取整**
>
> 先拿一批校准数据喂进模型，记录每一层输出的最大值最小值（**定标**）；然后把浮点区间均匀切成 256 份，每份对应一个整数（**取整**）。之后模型内所有运算都用整数做。
>
> 代价 = 精度损失；收益 = 体积变小、速度变快、能耗降低。对 ESP32-S3 这种内存以 KB 计、且常常没有浮点单元的芯片，这是**必须做**的一步。

## 2 怎么实现的（逐步拆解）

**1. 读 ONNX**
加载扩展 01 导出的 8.8 MB 模型

**2. 搭图像管线**
ImageFolder 读图 → 缩放 224×224 → 归一化

**3. 校准 + 量化**

**4. 导出产物**

这是本课相对微课 02 最大的新增部分，用 torchvision 的 `transforms` 搭：

```

### 坑 4 ★ ｜ 一跑就崩：老师脚本的 `collate_fn` 契约写错了

> **【修复】**
>
> **现象**
>
> ```
> Calibration Progress(Phase 1):   0%|          | 0/32
> RuntimeError: stack expects each tensor to be equal size,
>               but got [3, 224, 224] at entry 0 and [] at entry 1
>   at quantize_catdog.py:14
>       return torch.stack([sample[0] for sample in batch])
> ```

校准刚开始第一步就崩了。报错里 `[3,224,224]` 和 `[]` 这两个形状很关键——一个是图片，一个是空（标量）。

#### 根因：ESP-PPQ 对 `collate_fn` 的契约和老师的假设不一样

老师的写法假设 `batch` 是**一串样本**（每个样本是 `(图片, 标签)`），所以取每个样本的第 0 项再堆起来。这是**标准 DataLoader 的 collate\_fn 写法**。

但看 PPQ 的源码（`quantization/optim/calibration.py`）：

```
for data in dataloader:            # data 已经是 DataLoader 拼好的 batch
    if self._collate_fn is not None:
        data = self._collate_fn(data)     # 再调用一次
    executor.forward(inputs=data, ...)
```

**PPQ 的 `collate_fn` 拿到的是"已经拼好的整批数据"，它的职责只是预处理（转数据类型、搬到设备上），不是拼 batch。**名字有误导性——它不是 DataLoader 的那个 collate。

PPQ 官方示例写得很清楚：

```
def collate_fn(batch: torch.Tensor) -> torch.Tensor:
    return batch.to(DEVICE)
```

#### 为什么这次崩了，微课 02 却没崩？

PPQ 实际传进来的是 `list [ (8,3,224,224), (8,) ]`——图片批 + 标签批。老师的代码对每一项取 `[0]`：

- 对图片取 `[0]` → `[3,224,224]`（一张图）
- 对标签取 `[0]` → 0 维标量 `[]`

两个形状不一样，`torch.stack` 直接报错 → **崩得明明白白**。

而微课 02 里，x 和 y 的形状**恰好都是 `[32,1]`**，stack 得通，所以**没崩**——但含义完全错了（详见微课 02 的案例说明）。**同一个 bug，在微课 02 是静默的，在这里是崩溃的。**

#### 修正

老师原版 `quantize_catdog.py` **一字未动**（仍 1806 字节 / MD5 `3ac36cd119da40e5595f1b109ce366de`）。另存了一份修正版 `quantize_catdog_fixed.py`，只改 `collate_fn` 这一个函数：

```
def collate_fn(batch):
    if isinstance(batch, (list, tuple)):
        batch = batch[0]          # 丢掉 labels，只留 images
    return batch.to(torch.float32)
```

实测：原版崩溃；修正版输出 `(8, 3, 224, 224) torch.float32` ✓，`py_compile` 通过，一次跑通。

> **【通过】**
>
> **沉淀的排查方法**
>
> 遇到"函数被框架反复调用"的报错时，**先读框架源码确认调用契约**，不要假设参数含义。名字相同的函数，在不同框架里可能完全是两回事。

### 坑 5 ｜ 上游 ONNX 的时间戳可疑：比 .pth 晚了 16 分钟

> **【注意】**
>
> **现象**
>
> | 文件 | 大小 | 修改时间 |
> | --- | --- | --- |
> | catdog\_mobilenet\_v2.pth | 9,154,251 | 16:04:49 |
> | catdog\_mobilenet\_v2.onnx | 8,875,417 | 16:20:04 |

训练脚本里，存 `.pth` 和导出 `.onnx` 只隔几行代码，正常应该只差几秒。差 15 分钟，不得不怀疑"这个 ONNX 是不是来自别的 .pth"——如果源头不对，整个量化结果的验收前提就塌了。

#### 怎么验：直接从 .pth 重新导出，逐张量对比

第一步就碰壁：**按名字比对失败**——ONNX 里用的是 TorchScript 风格的名字（如 `onnx::Conv_538`），和 PyTorch 的 `features.0.weight` 对不上。

改用"形状 + 数值指纹"匹配，也只对上 2/108 个。正当以为"真的不是同一份"时，注意到一个细节：**ONNX 的值 / .pth 的值，比值是恒定的 5.0070534**。恒定比值不可能是巧合。

于是做了决定性实验：**从当前 `.pth` 重新导出一次 ONNX，和现存的那份对比**：

> **【通过】**
>
> **结果**
>
> **106 / 108 个张量逐位完全相同。**剩下 2 个是 `features.0` 里的常量张量，序列化方式略有差异（差 3,085 字节）。

#### 那个恒定的比值是什么？

进一步验证：这个比值**逐通道**等于 `BN.gamma / sqrt(BN.var + eps)`：

```
ONNX/.pth 比值  : [5.007054, 6.868892, 1.396138, 2.141298, 1.055915, 3.578236]
BN 折叠系数     : [5.007054, 6.868892, 1.396138, 2.141298, 1.055915, 3.578236]
                  ↑ 完全一致
```

> **【通过】**
>
> **结论**
>
> **ONNX 就是这份 .pth 导出的。**差异来自导出时的一个正常优化——**BatchNorm 折叠**。
>
> 推理时 BatchNorm 只是一个固定的线性变换（减均值、除标准差、再缩放平移），可以**数学上合并进前面的卷积层**，从而省掉一层的计算。PyTorch 导出 ONNX 时会自动做这个优化，所以卷积权重看起来"变了"，其实等价。
>
> **验收清单第 1 条成立。**

> **【说明】**
>
> **沉淀的经验**
>
> 核对"两个模型文件是不是同一份权重"时，**不要直接比张量值**——导出会做 BN 折叠 / 常量折叠，值本来就会变。
>
> 正确做法：**从 A 重新导出，与 B 逐张量比对。**

## 5 这一课收获了什么

1. **跑通了完整图像量化链路**：ONNX → 图像预处理 → 校准 → 8 位模型。这是从"玩具"走向"真实任务"的关键一步。
2. **认识了 BatchNorm 折叠**：推理时的等价变换，也是"为什么导出的模型权重看起来变了"的答案。
3. **学会了"重导出对拍"这个硬核验证手法**：不猜、不比表面值，用可控实验直接证伪或证实。
4. **再次验证了 `collate_fn` 契约问题**——而且这次是崩溃式的，比微课 02 的静默版更容易发现，正好互为印证。
5. **体会了"压缩比随模型变大而提高"**：微课 02 压到 42.2%，本课压到 26.73%。固定开销的占比效应。

> **【说明】**
>
> **与微课 02 的呼应**
>
> |  | 微课 02（sin） | 扩展 02（猫狗） |
> | --- | --- | --- |
> | 输入 ONNX | 18,244 B | 8,875,417 B |
> | 输出 .espdl | 7,696 B | 2,372,240 B |
> | 压缩后占比 | 42.2% | **26.73%** |

> 模型越大，权重压缩的收益越能充分体现——固定开销被摊薄了。
