## 1 这个方案到底在做什么

一句话：**用真实照片训练一个能分辨"猫"和"狗"的模型，然后导出 ONNX，为塞进 ESP32-S3 做准备。**

如果微课 01（sin 曲线）是"hello world"，扩展 01 就是**第一次上真实任务**。跨度很大：

|  | 微课 01（sin） | 扩展 01（猫狗） |
| --- | --- | --- |
| 数据 | 现算 1000 个点 | **2400 张真实照片**（要下载 55 MB） |
| 模型 | 3 层全连接，4353 参数 | **MobileNetV2**，约 220 万参数 |
| 输入 | 1 个数字 | **224×224×3 的图像** |
| 任务 | 回归（拟合曲线） | **分类**（猫 or 狗） |
| 设备 | CPU 13 秒 | **需要 GPU** |

### 两个关键选择

> **【说明】**
>
> **① 用 MobileNetV2 —— 因为它本来就是为端侧设计的**
>
> MobileNetV2 是 Google 专门为手机、单片机这类**算力受限设备**设计的网络。它用一种叫"深度可分离卷积"的技巧，把标准卷积的运算量砍掉 8~9 倍，精度却只掉一点点。后面要烧进 ESP32-S3，用它是最自然的选择。

> **【注意】**
>
> **② `weights=None` —— 从零开始训，不用预训练权重**
>
> 正常情况下，大家都会加载 ImageNet 预训练权重（"迁移学习"），几百张图就能有很好的效果。但本课脚本写的是 `weights=None`，意思是**完全从随机初始化开始学**。
>
> 为什么？因为课程要演示的是**完整的端侧链路**，而不是刷精度。从零训练有个好处：**不依赖外部下载的权重文件**，离线也能跑，链路更干净。
>
> 代价就是精度低——README 也预告了 **val\_acc 大概在 0.5~0.7**。这个数字看着"很差"，但**完全符合预期**，不是训练失败。

### 2.1 数据集

| 项目 | 内容 |
| --- | --- |
| 文件 | cats-dogs-data.zip |
| 大小 | **55,203,029 字节**（约 55 MB） |
| 结构 | cats-dogs-data/{train,valid}/{cat,dog} |
| 数量 | train: 1000 猫 + 1000 狗 ｜ valid: 200 猫 + 200 狗 = **2400 张** |

目录结构是 `类别名/图片` 的形式，正好能直接用 PyTorch 的 `ImageFolder` 读——**它会自动把子目录名当成类别标签**，并且按字母序排：`['cat', 'dog']`。这个顺序很重要，后面推理时"输出第 0 位 = 猫"就是从这里来的。

| 项目 | 取值 | 说明 |
| --- | --- | --- |

| 输入尺寸 | 224×224 | MobileNetV2 的标准输入 |
| 归一化 | ImageNet 均值/标准差 | 把像素值标准化到大致 [-2, 2.3] 区间 |
| 损失函数 | CrossEntropyLoss | 分类任务标准选择 |
| 轮数 | 3 | 课程设定，够看出趋势 |

## 4 遇到的问题（真实踩坑记录）

### 坑 1 ｜ 数据集下载：`curl -o` 会把已下的分片截断成 0 字节

> **【修复】**
>
> **现象**
>
> 下载到 2.7 MB 时网络断了。重新执行 `curl -L -o cats-dogs-data.zip URL`，**文件瞬间变成 0 字节**——之前的进度全没了。

**根因**：`curl -o` 是"从头开始写"，不带续传参数。文件一被打开就被清空。

**正确写法**：必须加 `-C -`（断点续传），并且自带重试：

```
curl -L -C - -o cats-dogs-data.zip "URL" ^
     --retry 30 --retry-delay 3 --retry-all-errors ^
     --speed-limit 2048 --speed-time 30
```

`--speed-limit 2048 --speed-time 30` 专门治"卡住不动"：30 秒内速度低于 2 KB/s 就自动断开重连。

#### 镜像选择也是坑

一开始推荐了两个 GitHub 加速镜像，结果用户白试——都连不上。后来实测各站点状态码：

| 地址 | 结果 | 能用吗 |
| --- | --- | --- |
| raw.githubusercontent.com | 206（支持 Range 续传） | 首选 |
| ghproxy.net | 206 | 备选 |
| ghfast.top / gh.llkk.cc / github.moeyy.xyz 等 | 连不上 | 不可用 |
| cdn.jsdelivr.net/gh | 403 | 不可用 jsDelivr 对 GitHub 文件限 20 MB，55 MB 必失败 |

**最终结果**：用 `raw.githubusercontent.com` 直连 + 断点续传 + 自动重试，前两次触发"太慢"自动重连，第三次成功。**耗时 5 分 33 秒，最终字节数 55,203,029——与目标分毫不差。**

> **【注意】**
>
> **教训**
>
> **不要在无法验证的情况下推荐下载地址。**这次让用户白试了镜像，浪费了时间。以后先探测状态码，确认能通再给。

### 坑 2 ｜ 两个 conda 环境，谁都跑不了这个脚本

> **【修复】**
>
> **现象**
>
> README 说用 `esp32s3` 环境（"比案例 1 多 torchvision"）。实际一跑：`ModuleNotFoundError: No module named 'torchvision'`。

| 包 | esp32s3 | torch\_gpu |
| --- | --- | --- |
| torch | 2.11.0+**cpu** | 2.11.0+cu128 |
| torchvision | **缺** | 0.26.0+cu128 |
| matplotlib | 3.10.8 | **缺** |

**结论**：`esp32s3` 缺 torchvision，`torch_gpu` 缺 matplotlib——**两个环境都跑不了**。必须给其中一个补一个包。

#### 补哪个？用 dry-run 决定

两个方案都用 `pip install --dry-run` 预演（零风险、不写盘）：

| 方案 | dry-run 结果 | 判定 |
| --- | --- | --- |
| 给 `torch_gpu` 装 matplotlib | Would install contourpy / cycler / fonttools / kiwisolver / matplotlib / pyparsing / six ——**全是新增** | 选它 零卸载零降级，还能吃 GPU |
| 给 `esp32s3` 装 torchvision | Would install **setuptools-81.0.0** + torchvision ——把 setuptools 从 83 降级 | 否决 危险动作 + CPU 训练慢几十倍 |

> **【通过】**
>
> **沉淀的通用手法**
>
> 给用户的任何 `pip install` 都先跑 `--dry-run`，看输出里的 `Would install` / `Would uninstall` 行。
>
> **"全是新增" = 安全；"出现卸载 / 降级" = 停手。**

### 坑 3 ｜ matplotlib 装好了却 import 失败 → 挖出"半残包"

> **【修复】**
>
> **现象**
>
> ```
> File "...\matplotlib\__init__.py", line 258, in _check_versions
> ModuleNotFoundError: No module named 'dateutil'
> ```

matplotlib 明明装成功了，却报缺少 `dateutil`。查下去发现：`python-dateutil` 的**元数据还在**（`python_dateutil-2.9.0.post0.dist-info`），但**代码目录整个不见了**。

这种包叫**半残包**：pip 认为"已安装"所以拒绝重装，import 时又找不到代码。**最坑的是它会伪装成"依赖缺失"。**

#### 写了个体检脚本，又挖出一个

为了彻底排查，写了一个环境体检脚本 `audit_env.py`：遍历所有已安装的包，逐个检查"元数据里记录的文件，实际在不在"。结果：

| 包 | 记录文件数 | 实际存在 | 判定 |
| --- | --- | --- | --- |
| protobuf 7.36.1 | 122 | **0** | 半残 |
| python-dateutil 2.9.0.post0 | 44 | **0** | 半残 |

全环境共 29 个发行包，其余正常。

#### 怎么修？不能用 pip

三种 pip 写法全部否决：

- `pip install` → 认为 already satisfied，**不干活**
- `pip install --force-reinstall` → 触发**卸载**，危险
- `pip install --ignore-installed` → 它的 dry-run **不报卸载**，无法证实安全

**改用 `install_whl.py`**：只做"下载 wheel + 解压覆盖到 site-packages"，**全程零删除**，不触发系统的安全拦截。

而且修之前先在**临时目录**隔离验证：把 wheel 解压到 `%TEMP%`，用 `PYTHONPATH` 指过去跑一次 import——确认没问题，才往真环境里装。

### 坑 4 ｜ 训练成功，导出 ONNX 却报 `AttributeError`

> **【修复】**
>
> **现象**
>
> ```
> AttributeError: module 'onnx' has no attribute 'load_model_from_string'
> ```

训练三轮全部跑完，产物存了 4 个，唯独 `.onnx` 没有——导出时炸了。

#### 根因：一个空目录在冒充"已安装的包"

查下去发现 `torch_gpu\Lib\site-packages\onnx\` 是一个**空目录**（0 个文件）。

> **【注意】**
>
> **为什么这么难查**
>
> - Python 3.3+ 会把这种目录当成**"命名空间包"**——`import onnx` **不报错**，但里面什么都是空的
> - 它连 dist-info 都没有，所以第一版体检脚本（只查"有元数据无代码"）**漏掉了它**
> - 报错发生在很靠后的位置，很容易误判成 torch 自己的 bug

这是**第三种损坏形态**，比"半残包"更阴——半残包至少还报 ModuleNotFoundError，这个连报都不报。

#### 修复与验证

同样先在临时目录隔离验证：下载 `onnx-1.17.0` 的 wheel，解压到 `%TEMP%\wb_onnx_iso\`，**拿真实的 `.pth` 跑一次完整导出**：

```
onnx.__version__ = 1.17.0
load_model_from_string: True      checker: True
导出成功 8,878,502 字节，onnx.checker.check_model 通过
输入 [('input',[1,3,224,224])]   输出 [('output',[1,2])]
```

而且验证时 `protobuf` 走的是环境里真实的 7.36.1 → 顺带证明了 **onnx 1.17.0 与 protobuf 7.36.1 兼容**。确认无误后才装进环境，重跑，导出成功。

体检脚本也随之升级，现在能覆盖三种损坏形态：A 半残包、B 空壳目录、C 无主代码。

### 坑 5 ★ ｜ 同一台机器、同一个 seed，跑两次结果不一样

> **【修复】**
>
> **现象**
>
> 第一次跑和第二次跑，参数完全相同（同机、同 seed 42、同数据、同脚本），**结果不同**：
>
> |  | epoch 1 | epoch 2 | epoch 3 |
> | --- | --- | --- | --- |
> | 第 1 次 | 0.67305 / 0.6225 | 0.66507 / 0.6400 | 0.65272 / 0.5900 |
> | 第 2 次 | 0.67087 / 0.6525 | 0.65789 / 0.6175 | 0.64559 / 0.6600 |

第一反应是"脚本有问题"。但查了脚本：第 50 行确实设了 `torch.manual_seed(args.seed)`，**除此之外没有任何随机性设置**。

#### 隔离实验：把前向和反向分开测

写了个最小实验，只做一次前向 + 一次反向，跑两遍对比：

```
cudnn.deterministic = False / benchmark = False / use_deterministic_algorithms = False

第 1 次   loss=0.7112174630   grad.sum=9.8749408722
第 2 次   loss=0.7112174630   grad.sum=9.8749370575

loss 相同: True      ← 前向完全确定
grad 相同: False     ← 反向每次不同
差异量级: 3.81e-06
```

> **【修复】**
>
> **根因**
>
> **cuDNN 的卷积反向传播用了带 `atomicAdd` 的非确定性算法。**
>
> GPU 上成千上万个线程同时往同一块内存里累加梯度，**加法的先后顺序是不定的**。而浮点加法不满足结合律——`(a+b)+c` 和 `a+(b+c)` 的结果在小数点后第 7 位就会不一样。
>
> 所以：**前向（只读）完全确定，反向（要累加）每次差 ~1e-6。**

每步差 1e-6 听起来微不足道，但一轮有 125 个 batch，误差**逐步累积**；而神经网络是**非线性系统**，微小的差异会被放大。到第 3 轮就变成了 0.002~0.007 量级的可见差异，几轮之后完全分岔。

> **【通过】**
>
> **这是本课最重要的认知**
>
> `torch.manual_seed()` **只管"随机数"（权重初始化、数据打乱），管不了 cuDNN 的算法非确定性**。
>
> "设了 seed 就能复现"是新手最大的误区之一。
>
> 要真复现，需要额外加：`torch.backends.cudnn.deterministic = True` + `torch.backends.cudnn.benchmark = False`，或者 `torch.use_deterministic_algorithms(True)`。**但老师原件不能改，这里只作说明。**

顺带发现 README 的一个缺口：配置说明里写 `--seed`（默认 42）"固定划分便于复现"——这个措辞本身没错（seed 确实只固定了数据划分），但**没有提醒 GPU 训练跑两次结果会不同**。
